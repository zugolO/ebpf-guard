# Список rule_id, классифицированных как ФОНОВЫЕ для критерия 6 run-gate.sh
# (волна 5.8a, находка №22 замера №2.4).
#
# Зачем этот файл. Критерий 6 требует final[r] > 0 в снимках /metrics
# attack-results (baseline→final того же прогона, что и атака — обычно
# 8-15 минут). Правила из этого списка либо не имеют шанса сработать под
# атакой вовсе (owasp_log_tampering/sigma_log_deletion срабатывают на
# rsyslogd, а не на действия атакующего), либо срабатывают на простое
# заметно чаще, чем успевает попасть в короткое окно атаки. Требовать от
# них final[r] > 0 именно в attack-results — значит путать «правило не
# сработало в этом узком окне» с «правило умерло», и печатать первое как
# регресс детекта (ровно находка №22).
#
# Правка run-gate.sh (5.8a): для правил из этого списка критерий 6 считает
# правило живым, если ЛИБО final[r] > 0 в attack-results (как раньше —
# самошум продолжается и под атакой почти всегда), ЛИБО есть прирост между
# IDLE_METRICS_START и IDLE_METRICS_END (снимки idle-run.sh) — OR, а не
# замена: это не ослабляет проверку для правил, которые действительно
# пропали и там, и там, а только снимает ложный "лост" с правил, живых на
# простое, но не подвернувшихся под короткое окно атаки. Если
# IDLE_METRICS_START/END не переданы, сторона по idle пропускается с явной
# пометкой SKIP, а не тихим PASS (непроверенное не засчитывается ни в
# одну сторону — принцип волны 1.75).
#
# КАК ПОЛУЧЕН СПИСОК (механически): правило считается фоновым, если дало
# >= 10 алертов за idle-час замера №2.4 (idle/idle-20260817_153403/
# alerts-start.json → alerts-end.json, дельта по rule_id — по СТОРУ, как и
# первая редакция этого файла) и присутствует в detection-baseline.txt.
#
# ПОЧЕМУ ИМЕННО 10/ч, а не >= 1/ч, как в первой редакции. Первая редакция
# применяла формулировку 5.8a буквально («дало >= 1 алерт за idle-час»), и
# в список попали 23 правила, включая четыре с частотой 6-8 за ВЕСЬ час —
# то есть события, случающиеся раз в 8-10 минут, а не постоянный фон
# демона. Из-за этого они выходили из-под требования сработать под атакой,
# хотя находка №22 говорила ровно про постоянный фон (rsyslogd), и итог
# пересчёта расходился с предсказанием 5.8a (4 потери вместо 7).
#
# Порог не подобран под предсказание, а взят по разрыву в самих данных
# №2.4 — распределение дельт за idle-час обрывается ровно здесь:
#   ... 34, 23  |  8, 7, 7, 7, 6, 3, 3, 1, 1, 1, 1, 1
# то есть между 23/ч и 8/ч разрыв втрое, а ниже — только редкий хвост.
# 10/ч = «хотя бы раз в 6 минут» лежит внутри этого разрыва, и любое
# значение от 9 до 22 дало бы тот же список. Совпадение с предсказанием
# 5.8a (потери = 7 сетевых типов) — следствие, а не цель.
#
# Выбыли по сравнению с редакцией >= 1/ч (6 правил): incident_confirmed_attack
# (8/ч), initial_package_postinstall_network (7), netintr_large_upload_port (7),
# netintr_syn_scan_pattern (7), netintr_long_dns_session (6),
# webshell_script_write_via_web_process (3). Все шесть снова обязаны
# срабатывать под атакой, как и до 5.8a.
