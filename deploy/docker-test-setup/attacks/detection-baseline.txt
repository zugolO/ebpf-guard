# Базовый СОСТАВ типов детекта (rule_id), критерий 6 run-gate.sh.
#
# Зачем состав, а не число (волна 5.3, находка №2 замера №2). Порог «>= 43 типа»
# был снят с прогона №4 и стал недостижим после законного сужения правил: замер
# №2 дал 41 тип и FAIL, хотя ни один настоящий детект не пропал — часть типов
# перестала срабатывать потому, что была FP и её сузили намеренно. Одно число не
# отличает «детект просел» от «FP перестал считаться детектом», и разбирать это
# пришлось руками. Гейт теперь печатает diff: потеряно / добавлено.
#
# Основание: замер №2 (TIMESTAMP=20260806_154041), 1096 новых алертов за прогон,
# 41 уникальный rule_id. Список снят с него как есть — это фиксация факта, а не
# целевое состояние.
#
# Как обновлять. Diff — это не автоматический провал: «добавлено» после волны,
# которая заводит правила, ожидаемо; «потеряно» после волны, которая правило
# намеренно сузила или переименовала, — тоже. Провалом считается потеря, которую
# никто не объяснил. Обновлять файл ТОЛЬКО вместе с записью в plan.md о том,
# какая волна и почему изменила состав, иначе база теряет смысл основания.
#
# Известное расхождение к замеру №2.1: волна 5.1 раздвоила семь правил кластера
# на базовое и *_daemon. В этом списке уже есть sigma_utmp_wtmp_modified_daemon
# (правило существовало до 5.1), а остальные шесть записаны в базовых именах —
# после 5.1 в diff ожидаются добавления вида *_daemon при сохранении базовых.
# Это ожидаемое «добавлено», не потеря.
#
# Обновление 5.5b (находка №7 замера №2.1): критерий 6 напечатал FAIL на пяти
# типах при исправном детекте — все пять присутствуют в alerts_filtered_total
# замера №2.1, просто их не стало в alerts_total/store после 5.1a (фильтр info
# на входе идёт ниже IncidentTracker, но выше сериализации alerts_total/store).
# Удалены из базы как отдельные строки (не «переименованы» — гейт сравнивает
# rule_id по alerts_total, а не по alerts_filtered_total). Два разных случая,
# свёрнутых в один симптом:
#   - rootkit_pam_module_added, sigma_failed_login_syscall — базовые имена
#     кластера волны 5.1; сейчас на idle/этом прогоне срабатывает только
#     *_daemon-двойник (severity info). Базовое имя остаётся валидным
#     rule_id — сработает и попадёт в alerts_total, если тронет процесс
#     вне [sshd, cron] — просто не в этом прогоне.
#   - sigma_utmp_wtmp_modified_daemon — было в базе уже с суффиксом (родилось
#     _daemon в P1-6, до волны 5.1); волна 5.1 поменяла только severity
#     warning → info — другая запись, не переименование.
#   - c2_periodic_beacon_pattern, recon_sensitive_file_find — НЕ из кластера
#     волны 5.1, severity: info изначально; тот же фильтр 5.1a впервые их
#     коснулся на этом прогоне. Ничего не переименовано, не тронуто волной 5.1.
# Если любой из пяти снова понадобится в базе — то с тем же типом записи, что
# здесь: строка + причина в этом файле и в plan.md (5.5b), а не тихий возврат.
# Добавлено: owasp_log_tampering — новое срабатывание правила (замер №2.1),
# не регресс и не связано с находкой №7.
