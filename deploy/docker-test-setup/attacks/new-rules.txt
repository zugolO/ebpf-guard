# new-rules.txt — волна 6.0f (реплей-блокер правки №200): реестр правил,
# ЗАВЕДЁННЫХ ПОЗЖЕ архивов, на которых гоняется replay-gate.sh.
#
# Зачем. Реестры критерия 6 (detection-baseline.txt) читаются в ТЕКУЩЕМ
# составе правил, а архивы реплеев сняты тогда, когда части этих правил ещё
# не существовало. Правило, добавленное сегодняшней волной, по построению
# немо на КАЖДОМ архиве старше себя: критерий 6 печатает его потерей, 5.9.4h
# вслед за ним — «категорией (в) без объяснения», и ЖЁСТКИЙ СТОП №1
# пайплайна встаёт, хотя ни продукт, ни гейт не регрессировали. Ровно это и
# случилось с container_escape_host_device_from_host (правка №200 волны
# 6.0f): три реплея (8/22, 11/22 ×2, 21/22) разошлись с зафиксированным
# исходом на следующий же прогон после разведения правила.
#
# Отличие от соседних реестров. renamed-rules.txt (№170) лечит СМЕНУ ИМЕНИ —
# там правило в архиве есть, просто под старым id; здесь правила в архиве
# нет вовсе. silent-rules.txt объясняет немоту НА ЭТОМ стенде — запись туда
# утверждала бы, что стенд не воспроизводит сценарий, что для правки №200
# ложь: сценарий воспроизводит контроль 6.0.13 (dumpe2fs на хосте) в этом же
# пайплайне, и правило обязано срабатывать на живом прогоне.
#
# Что делает гейт. Правило исключается из потерь и из 5.9.4h ТОЛЬКО когда
# дата прогона (первые 8 цифр TIMESTAMP, YYYYMMDD) СТРОГО РАНЬШЕ даты
# заведения правила. На прогоне своей волны и на всех последующих правило не
# исключается ничем и обязано либо сработать, либо честно быть потерей —
# то есть запись здесь не может ослепить будущий замер, в отличие от строки
# в silent-rules.txt, которая действует вечно.
#
# ФОРМАТ (табуляция): <rule_id> <YYYYMMDD заведения> <пункт волны>

# ── Волна 6.2.1 (2026-09-05, находка №220): правила, СУЖЕННЫЕ этой волной ──
#
# Почему они здесь, а не в renamed-rules.txt. run-6.2.1-pipeline.sh шаг 0
# сначала предписывал «каждое сужённое правило — в renamed-rules.txt с датой
# этого прогона», и это привело бы к ПРЕФЛАЙТ FAIL (run-gate.sh:423, сторож
# №170): запись там обязана быть переименованием — старого id в rules/ уже
# нет, нового есть. У сужения id не меняется, обе половины сторожа не
# выполняются, и цепочка встала бы до чтения снимков. Механика ЭТОГО реестра
# подходит по существу: вычитание из потерь действует ТОЛЬКО на архивах
# СТАРШЕ даты записи, на собственном прогоне волны и на всех последующих
# правило обязано либо сработать, либо честно быть потерей. silent-rules.txt
# не годится — та строка бессрочна.
#
# Почему не все сужённые правила. Сужения по comm (k3s-server, coredns,
# containerd, local-path-prov) на старых архивах не меняют НИЧЕГО: этих comm
# там нет, правило сработает ровно как раньше. Запись им не выписана — она
# маскировала бы настоящий регресс. Здесь только те пять, у которых изменено
# САМО условие, и потому старый архив может недосчитаться их законно:
#   container_escape_host_mount / container_escape_host_network — добавлено
#       требование контейнерного контекста (container.id или k8s.pod непусты).
#       На старых архивах их поднимали ХОСТОВЫЕ процессы, значит правило
#       замолчит. container_escape_host_mount есть в detection-baseline.txt —
#       без этой записи реплей любого архива старше 04.09.2026 даст ЖЁСТКИЙ
#       СТОП №1 без единого регресса продукта (тот же класс, что правка №200).
#   cryptominer_xmrig_signature — сняты паттерны 'config\.json'/'pools\.txt'
#       без привязки к xmrig: они ловили любой config.json на диске.
#   evasion_iptables_flush / sigma_iptables_flush — добавлена проверка самих
#       флагов (-F/--flush/-X/--delete-chain как ОТДЕЛЬНЫХ аргументов).
#       Прежние условия срабатывали на любом exec iptables и на подстроку
#       "-F" внутри имени цепочки (FLANNEL-FWD), то есть на архивах могли
#       быть подняты чем угодно, что запускало iptables.

# ── Волна 6.2.1, слой 3 (2026-09-05, находка №220): chmod переехал на ось ───
# файловых событий. До этой волны chmod был виден ТОЛЬКО как номер сисколла
# (90/91/268), где аргументы — сырые указатели, поэтому все три правила ниже
# несли ровно одно условие — «случился chmod» — и давали три алерта на каждый
# chmod любого файла (144 из 1787 алертов окна замера 6.2). Теперь
# bpf/fileaccess.bpf.c хукает chmod/fchmodat (путь из user space) и fchmod
# (путь из своей же fd_path_map), правила стоят на event_type: file и
# проверяют путь — каждое свой.
#
# Почему запись нужна. На архивах старше этой даты события chmod приходили
# ТОЛЬКО syscall-событиями: файлового chmod там нет физически, значит правила
# на реплее немы по построению — тот же класс, что правка №200. На собственном
# прогоне волны и на всех последующих вычитания нет, и правила обязаны либо
# сработать, либо честно быть потерей. Живой позитивный контроль есть в
# пайплайне (6.2.1.9: chmod +x канарейки в /tmp и chmod системного бинаря),
# так что silent-rules.txt здесь был бы ложью.
#
# ВНИМАНИЕ на дату. Вычитание срабатывает при СТРОГОМ run_date < даты записи
# (run-gate.sh:1459), поэтому запись, датированная днём самого архива, этот
# архив НЕ покрывает. Записи волны выше по этой причине передатированы с
# 20260904 на 20260905: архив collect-6.2 снят 04.09.2026, и при равных датах
# реплей давал бы ЖЁСТКИЙ СТОП №1 без единого регресса продукта.
