# Реестр правил с нулевым ebpf_guard_alerts_total за ВЕСЬ аптайм агента
# (не за окно прогона — за жизнь процесса), волна 5.9.4h, находка №59.
#
# Отличие от intentional-loss.txt/background-rules.txt: те списки — про
# критерий 6 (состав детекта в ОДНОМ прогоне, окно атаки ± idle-час).
# Этот файл — про отдельный машинный гейт: любое правило, немое за весь
# аптайм, обязано быть здесь с категорией, иначе run-gate.sh проваливает
# его как категорию (в) «без объяснения» (см. run-gate.sh, секция
# "правила, немые за весь аптайм").
#
# ФОРМАТ: одна строка на правило — "<rule_id> <категория>", без хвостовых
# комментариев на той же строке (пояснение — отдельным блоком выше списка,
# как в intentional-loss.txt). Категории:
#   a — немо по конструкции (ловится UnreachableSyscallRules/
#       ContextEmptySyscallRules — недостижимый nr или условие без
#       контекста; см. соответствующий rules_coverage_test.go)
#   b — немо из-за среды: условие корректно и достижимо, но этот стенд не
#       воспроизводит сценарий, который бы его вызвал (ни на простое, ни
#       под атакой). Снимается волной 6 добавлением сценария, не правкой
#       правила.
# Категория (в) «без объяснения» в этом файле не имеет строк по
# построению — она и есть множество, не попавшее сюда.
#
# ─────────────────────────────────────────────────────────────────────────────
# Волна 5.9.4h (находка №59): три правила из таблицы находки №57, не
# сработавшие НИ РАЗУ ни на одном известном прогоне (№2.9.2, №2.9.3),
# в отличие от восьми соседей по той же таблице, у которых была история FP
# (см. intentional-loss.txt, блок 5.9.4f). Все три — event_type: file с
# условием на конкретные filename, синтаксически корректны и достижимы
# (FileaccessCollector трекает open(2) по умолчанию, internal/collector/
# fileaccess.go); ни один сценарий в run-all-attacks.sh не открывает эти
# пути:
#   sigma_cpu_info_access    — /proc/cpuinfo, /proc/meminfo, /proc/version,
#       /proc/sys/kernel/{hostname,osrelease,version}: разведка через
#       чтение системных файлов, у атаки на этом стенде нет шага, который
#       бы их открывал (собственные exceptions правила гасят чтения самого
#       ebpf-guard/pgrep).
#   sigma_kernel_version_read — /proc/version, /etc/*-release: OS
#       fingerprinting, тот же случай: нет attack-шага.
#   sigma_memory_proc_dump   — /proc/[pid]/{mem,maps,environ,cmdline}:
#       дамп памяти чужого процесса, нет attack-шага (кроме штатных
#       чтений systemd-journal, исключённых в самом правиле).
#
# web_sql_injection_files — четвёртое правило из находки №59, отдельное от
# трёх выше: единственный исторический экземпляр (2 алерта на
# systemd-logind, №2.9.2) был FP, убитым узким контекстом волны 5.9.3b
# (см. intentional-loss.txt, блок 5.9.4f) — искать в этом файле его
# больше нечему. Условие — SQL-паттерны в ИМЕНИ файла (union select, DROP
# TABLE и т.п. как подстрока filename); ни один сценарий SQLi в
# run-all-attacks.sh не создаёт файл с таким именем — инъекция идёт через
# сетевой запрос, а не через запись на диск. Категория та же: нет входных
# данных, не дефект правила.
#
# Волна 6 добавляет сценарий: reconnaissance-шаг (cat /proc/cpuinfo,
# /proc/version, /etc/os-release), чтение /proc/<pid>/mem инструментом
# вроде gdb/procdump, и webshell-загрузку с SQLi-паттерном в имени файла —
# после чего все четыре либо срабатывают и уходят из этого списка, либо
# остаются здесь по новой, более конкретной причине.
sigma_cpu_info_access b
sigma_kernel_version_read b
sigma_memory_proc_dump b
web_sql_injection_files b
